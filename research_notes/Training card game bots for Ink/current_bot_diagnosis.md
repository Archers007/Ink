# Current state of the Ink bot (first-hand reading of the repository, 2026-11-23)

Source: direct reading of the code in the Ink repository (a Disney Lorcana deck builder + online table, Node.js 22,
no ML dependencies; `package.json` has only express, ws, three, dotenv). These are primary observations, not web
research. File references are repo-relative.

## What exists

### 1. Quick bot / rollout policy — `game/bot.js` (232 lines)
A fixed-priority script, one action at a time: ink a card (scored by a few rules: spells +20, "too expensive" +30,
castable soon −20, duplicates +8) → play the most expensive affordable card (`val = cost*10 + 5 if character + lore`)
→ boost → quest if it wins this turn → the best "profitable" challenge (kills and survives: `12 + cost + 2*lore`)
→ quest with everything → end turn. Effect targets: "hurt their most expensive card, help my most expensive card",
always option 0 on modal choices, always "yes" on optional effects. Mulligan: ship cost ≥ 6 cards etc.
It never holds a card back, never plans around the opponent's next turn, has no concept of tempo, removal value,
card advantage, lore race, or the opponent's deck.

### 2. Hard bot — `game/searchbot.js` (352 lines)
"Determinized Monte Carlo search", but it is **flat, one-ply, root-only**:
- Enumerates the legal *single actions* right now (ink X / play Y / quest Z / challenge A→B / end turn / one
  pending choice), deduped by card id.
- Each sample: `structuredClone` the full state, re-deal hidden information (opponent hand/deck/inkwell shuffled
  from decklist minus seen cards — the bot is given the opponent's **exact decklist**; own deck shuffled), apply the
  candidate action, then **both sides are played by the quick bot (bot.js)** until the start of the searcher's own
  next turn, then score with a hand-written evaluation.
- UCB1-tuned allocates samples across the root actions only. No tree below the root. 450 ms per decision in the
  lobby (`HARD_BUDGET_MS`), single worker thread.
- A turn is a *sequence* of 5–15 actions; the search re-runs from scratch for each one, and everything after the
  first action in the same turn is played by the quick bot inside the sample. So the search really answers "which
  first action is best if the scripted bot finishes my turn and plays the opponent's whole turn", not "what is the
  best turn".
- Horizon = start of own next turn (about 1 full turn cycle). Anything that pays off later (inking, card
  advantage, developing instead of questing) is only visible through hand-tuned constants in the evaluation; the
  code comments document several patches of exactly this kind (ink worth 4 per ink up to six, "lethal" term, an
  ORDER tie-break because "the samples can't tell those orders apart", issue #21 where the bot stopped inking).
- Evaluation (`handEvaluate`): lore*4 (+3 per lore past 14), per-character `2 + lore*3 + (str+wp)*0.45`,
  hand size*1.4, ink terms, deck-out penalty, an exact "20 lore on board" lethal term. **No card identity, no
  abilities, no keywords** (evasive, ward, bodyguard, rush, singer, shift targets, location synergies… are invisible
  to the evaluation except through what happens inside one turn of scripted rollout).
- Opponent model: the scripted quick bot. The search therefore optimizes against an opponent that never holds
  removal, never plays around anything, always quests with everything.
- Hidden information: uniform random re-deal; no inference from the opponent's behaviour (e.g. what they inked or
  did not play), each determinization is perfect-information (classic PIMC → strategy fusion: it can "know" the
  opponent's hand inside a sample because the rollout policy for the opponent acts on the sampled hand).

### 3. The "model" — `game/learn/` (features.js, model.js, train.js)
- A **logistic regression over 21 hand-made aggregate features** (my/their lore, lore past 14, character count,
  total quest lore, total strength, willpower left, hand size, ink, items+locations count, deck low, turn).
  No card identities, no per-card features, no hand contents, no deck/archetype information.
- Training data: one position per turn start from saved games; label = did the player to move eventually win.
  Games are: lobby games (people vs bot, weighted 3×) and "self-play" generated by `scripts/train-bot.mjs
  --selfplay N`, which is the **scripted quick bot playing itself** (not the search bot).
- Fit: full-batch gradient descent, 400 epochs, written by hand in JS. Hold-out: every 5th game.
- Use: `evaluate = handEvaluate + 0.5 * 100 * (2*winProb − 1)`; only switched on if the search bot with it beats the
  search bot without it ≥ 60% over 80 games at 150 ms. The code comments already record the failure mode:
  "a model fitted to games where everyone inks every turn decides that a big hand wins, and stops inking".
- There is **no policy learning** (nothing learns which move to make), **no iteration** (the data is never
  regenerated by the improved bot), and the value target is the outcome under *weak scripted play*, which is not the
  value under good play.
- "Habits": per-card counts of what people did (ink vs play, mulligan keep vs ship) used by the quick bot when a
  card has ≥ 15 observations.

### 4. Infrastructure that already exists and is reusable
- A complete, deterministic rules engine (`game/engine.js`, `applyAction(state, seat, action)`, seeded RNG) that
  runs all 2,680 cards ("2680/2680 fully runnable").
- Replays stored as seed + decklists + action list (`lib/replays.js`, `game/learn/replay.js`), so every position of
  every game played on the site can be regenerated; human games are saved.
- An arena for A/B testing (`scripts/bot-arena.mjs`) with paired seeds and seat/deck alternation, 12 current meta
  decklists (`game/decks/meta.json`) fetched from dreamborn.ink.
- A game review feature (chess.com style move ratings) and a coach, both driven by the same search — so a stronger
  search/eval improves three features at once.
- A worker thread for the search bot (`game/botworker.js`), a training worker that retrains every 10 new games.

## Structural reasons it plays poorly (hypotheses from the code, to be checked against measurements below)
1. The learned part is tiny and blind: 21 aggregate features, linear, no card identity. It cannot represent
   anything a Lorcana player would call strategy.
2. The value labels come from weak play (scripted bot self-play), and nothing closes the loop (no generate →
   train → generate cycle with the improved player).
3. The search is one ply deep over single actions and delegates the rest of the turn and the entire opponent turn
   to a script. Sequencing within a turn (the core skill of the game) is not searched.
4. The search horizon is one turn cycle with a hand-tuned evaluation at the end; long-term value has to be
   hand-coded.
5. The opponent is modelled as the script; hidden information is re-dealt uniformly with no inference.
6. Cost per sample is dominated by `structuredClone` of an ~88 KB state (measured below), limiting samples per move.
